# AgentMark

## Versioning

- Every change that is built and installed gets a version bump, at least the patch number, so the running build is identifiable (`agentmark --version`, `chrome://extensions`)
- The CLI embeds the extension and the desktop app bundles the CLI, so all three share one version. Bump all of these together: `packages/cli/Cargo.toml`, `packages/extension/manifest.json`, `packages/extension/package.json`, the two root entries in `packages/extension/package-lock.json`, `packages/app/src-tauri/Cargo.toml`, `packages/app/src-tauri/tauri.conf.json` (`version`), `packages/app/package.json`, and the two root entries in `packages/app/package-lock.json` (`Cargo.lock` follows on the next build). Tests fail if any of them disagree

## Repository Structure

- `packages/cli/` — Rust CLI (`agentmark` binary), built with `cargo build`
- `packages/extension/` — Chrome MV3 extension (React + Vite + Tailwind + TypeScript)
- `packages/app/` — Tauri v2 desktop app (`src-tauri/`, crate `agentmark-app`; frontend `src/`, React + Vite + Tailwind + TypeScript)
- `packages/skill/` — Cross-agent skill definition and installer

## Rust CLI

- Workspace root `Cargo.toml`: members `packages/cli` and `packages/app/src-tauri`, `default-members = ["packages/cli"]` so root cargo commands never build the desktop app (Linux CI has no WebKit); the app builds with `-p agentmark-app`
- Lib/bin split: `src/lib.rs` exposes `agent`, `bundle`, `canonical`, `cli`, `commands`, `config`, `db`, `display`, `enrich`, `extension`, `extract`, `fetch`, `models`, `native`, `setup` modules; `src/main.rs` is a thin wrapper
- Extension embedding: `src/extension.rs` uses `include_dir!` to embed the pre-built Chrome extension `dist/` at compile time. `build.rs` ensures the `dist/` directory exists (creating an empty placeholder if needed) so compilation succeeds even without a prior extension build. The `install-extension` command extracts embedded files and registers the native messaging host
- Agent layer lives in `src/agent/` (`mod.rs`, `provider.rs`, `prompt.rs`, `claude.rs`, `codex.rs`, `pi.rs`) — LLM provider abstraction for enrichment (`enrich`) and page-to-markdown rendering (`render_article`) via local CLI subprocesses. `RealRunner` appends well-known user bin dirs to `PATH` because Chrome starts the native host with a bare system `PATH`. Uses an injected `ProcessRunner` trait for testable subprocess invocation. Providers are selected by `create_provider()` factory based on `config.default_agent`. Tests use mock runners rather than real CLIs or PATH mutation
- Canonical layer lives in `src/canonical.rs` — pure URL normalization (strip tracking params, normalize host/scheme/slashes, sort query params), depends only on `url` crate
- Domain model types live in `src/models/` (`bookmark.rs`, `event.rs`) — pure data + serde, no I/O or config coupling
- Database layer lives in `src/db/` (`mod.rs`, `schema.rs`, `repository.rs`) — SQLite + FTS5 index, depends on `models` and (for the v2 backfill only) the pure `canonical` module
- `bookmark_urls` (schema v2) maps every canonical URL a bookmark has been seen under to its id. `insert`/`update` record the bookmark's own `canonical_url`, `save.rs` adds the requested URL's canonical, and a trigger deletes rows with the bookmark. The native `lookup_urls` message reads it (`saved_urls`) to tell the extension which URLs are saved. Dedup (`get_by_canonical_url`) does not consult it
- Display layer lives in `src/display.rs` — shared terminal display helpers for list/show/search output (truncation, tag merging, width detection, color capability, list row formatting, show detail formatting). Pure functions returning strings; commands print
- Bundle layer lives in `src/bundle/` (`mod.rs`, `bookmark_md.rs`, `writer.rs`) — filesystem bundle creation + in-place updates + bookmark.md rendering + event append + read helpers (`read_article_md`, `read_body_sections`), depends on `models` + `fetch::PageMetadata`. `Bundle::find` locates existing bundles by `saved_at` + `id` suffix; update helpers preserve body sections during front-matter changes
- Extract layer lives in `src/extract/` (`mod.rs`, `readability.rs`, `to_markdown.rs`, `simplify.rs`) — article extraction + markdown conversion + content hashing, plus `simplify_html` (compact page skeleton for model input), depends only on readability/scraper/sha2
- Fetch layer lives in `src/fetch/` (`mod.rs`, `metadata.rs`) — HTTP fetch + metadata extraction, depends only on reqwest/scraper/url
- Config lives at `~/.agentmark/config.toml`, index DB at `~/.agentmark/index.db`
- DB layer accepts explicit paths/connections; `config.rs` remains the only HOME-aware module
- Setup core lives in `src/setup/` (`mod.rs`, `config_edit.rs`, `agents.rs`, `folder.rs`, `extension_ids.rs`, `install.rs`, `liveness.rs`, tests in `tests.rs`) — one implementation for the native host, `agentmark init` and the desktop app; `docs/setup-contract.md` is the contract for its types, rules and wire shapes. `read_state` never fails; `apply_settings` validates every field (relative storage paths are rejected), then creates the folder, writes `config.toml` and migrates the index. It is the only writer of `config.toml`: a `toml_edit` in-place edit that keeps comments and unknown keys, replaces a value only when it changes, moves an unparseable file aside, and writes atomically (`write_file_atomic`). Agent detection only stats files on `SetupEnv.search_path`. The folder dialog is behind the `FolderDialog` trait (`SystemFolderDialog` runs `osascript` / `zenity` / `kdialog` found on the agent search path); tests use a fake dialog or a fake dialog program on `PATH`
- Native host setup gate: `save`, `list`, `show`, `update`, `list_collections`, `lookup_urls` return `OutgoingMessage::setup_required()` (`error` with `code: "setup_required"`, message prefixed `not initialized`) until `setup::is_set_up`; `status` (with `initialized`), `get_setup_state`, `save_settings`, `choose_folder` work before setup. `main.rs` passes Chrome's origin argument to `native-host`; the host writes `~/.agentmark/extension-connection.json` (best effort, after the reply) at start and when a new `status.extension_version` arrives
- Native host manifests: `setup::register_native_hosts` writes `com.agentmark.native.json` for Chrome always and Chromium, Edge, Brave, Arc only when their data dir exists, allowing `WEB_STORE_EXTENSION_ID` (`oepdfndmpcpimbkaaocgolenncdkljeo`, also in the extension's `src/shared/constants.ts`; tests check the two match and that the manifest `key` gives it) plus development IDs persisted in `~/.agentmark/native-host.json` (migrated once from existing manifests). The registered path is `~/.agentmark/bin/agentmark` when it exists; `install_cli` copies a CLI there and never downgrades
- Commands are in `src/commands/` module tree (`init.rs`, `save.rs`, `list.rs`, `show.rs`, `search.rs`, `tag.rs`, `collections.rs`, `open.rs`, `reprocess.rs`, `delete.rs`, `install_extension.rs`)
- Shared detail/update helper lives in `src/commands/bookmark_detail.rs` — canonical DB+bundle detail loading and typed update application used by both `show.rs` (CLI) and `native_host.rs` (extension). Do not duplicate detail assembly logic in command handlers
- Browser snapshots: the extension sends the live tab's HTML as `page_html`. For URLs matching `src/snapshot_rules.rs` (built-in LinkedIn profile/post/company rules, X/Twitter site-wide, Hacker News discussions, Reddit site-wide, plus `snapshot_sites` in config) the snapshot is the content and the CLI's fetch is kept as a supplement in the bundle's `fetched.html` and as the preferred metadata source. For all other URLs `save.rs` uses the snapshot only when the CLI's own fetch fails (login walls, bot blocking). Do not add per-site HTML extractors — site-specific pages are rendered to `article.md` by the agent
- Site-specific *sources* live in the CLI, not the extension: the extension captures every page the same way, and `save.rs` decides by URL how to get the content. `src/youtube.rs` captures video pages through the optional `yt-dlp` CLI (metadata, chapters, captions rendered as the article) and falls back to a normal page save when it is missing or fails; it reuses the agent layer's `ProcessRunner` seam, so tests use a fake runner
- Native-host saves set `defer_enrichment` and never wait on a model: the host starts the hidden `agentmark post-process <id> [--render-article]` command (`commands/post_process.rs`) as a detached process, which renders `article.md` from `source.html` for snapshot saves and then runs enrichment. `content_hash` stays the hash of the captured page so re-saving the same page is `Unchanged`
- Command handlers return `Result<()>` — `main.rs` converts errors to stderr + non-zero exit
- Save command (`commands/save.rs`) is the integration boundary for canonical → fetch → extract → bundle → DB; uses typed `SaveError`/`SaveOutcome`/`DedupResult` with two-stage canonical dedup (pre-fetch + post-fetch), three-way branching (new/unchanged/changed), merge semantics for user-owned fields, and partial-save semantics (bundle preserved if DB update fails)
- `agentmark init` uses the setup core (default folder `~/Documents/AgentMark`); any of `--storage-path`, `--agent`, `--summaries on|off`, `--yes` makes it non-interactive
- Run checks: `cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo build && cargo test`
- Tests use `tempfile` for temp HOME dirs and `assert_cmd` for binary integration tests

## Chrome Extension

- Package-local npm project (no root `package.json` or workspace)
- All commands run from `packages/extension/`:
  - `npm ci` — install dependencies
  - `npm run typecheck` — TypeScript strict checking via `tsc --noEmit`
  - `npm run build` — Vite multi-entry build producing `dist/`
  - `npm run lint` — ESLint with flat config
  - `npm run test` — Vitest unit tests (Node environment with Chrome API mocks)
- `manifest.json` is static (root of `packages/extension/`), copied into `dist/` by `vite-plugin-static-copy`. It carries `key` (the Web Store item's public key), so any unpacked copy, including the one the CLI embeds and `install-extension` writes to `~/.agentmark/extension`, gets the store ID `WEB_STORE_EXTENSION_ID`. `npm run build:store-zip` (`scripts/build-store-zip.sh`) removes `key` from the store zip; do not remove it from `manifest.json`
- Build outputs: popup HTML, sidepanel HTML, background service worker (`background.js`), and content scripts under `content/`
- Internal seams: `src/background/`, `src/popup/`, `src/sidepanel/`, `src/shared/`, `src/content/`
- Content scripts (`src/content/`) add a per-item save button on LinkedIn, X, Hacker News and Reddit (posts and comments, www and old). `save-button.ts` is the site-agnostic core (button, states, snapshot, hand-off); each site is a `SiteAdapter` (`linkedin-posts.ts`, `x-posts.ts`, `hn-posts.ts`, `reddit-posts.ts`) chosen by hostname in `site-adapters.ts`. Reddit's controls live in shadow roots, so its button is a light-DOM child shown through a named slot (`findSlot` returns `slot`). Snapshots never include chat, inbox or notification elements: the rules are `PRIVACY` in `src/content/private-content.ts` (also the pages that get no buttons), mirrored for whole-page snapshots as `SNAPSHOT_PRIVACY` (`SnapshotPrivacy`) in `src/shared/page-snapshot.ts` for `capturePageHtml`; `private-content.test.ts` fails when the two drift. A click sends `open_save_popup`; the service worker stashes the save and opens the toolbar popup, which takes it via `take_pending_save` and saves it like a page (falling back to a direct save if the popup cannot open), then reports the result to the tab. After each injection pass, `saved-lookup.ts` sends one batched `lookup_urls` message (≤200 URLs each) for unchecked buttons and caches answers and successful saves per page; only buttons still idle are repainted (plain saved look), and every lookup failure is silent. `linkedin-urn.ts` (MAIN world, LinkedIn only) reads the post URN from LinkedIn's React data, the only place a timeline post's ID exists. Each `*.entry.ts` must bundle to one self-contained classic script: do not import `src/shared/` modules from content scripts or share a module between the two entries (Rollup would emit a shared chunk), and keep the constants duplicated between the two bundles in sync (a test checks them). Content scripts must never click or navigate the page
- Icons: SVG sources live in `packages/extension/icons/` (outside `public/`, so they do not ship); `icons/build.sh` (needs `rsvg-convert`) renders them into `public/icons/`. `icon-{16,32,48,128}.png` (from `icon.svg`) is the listing and notification icon (`manifest.icons`, `iconUrl`); `toolbar-<look>-{16,32,48}.png` are the per-tab toolbar looks: idle (hollow grey), saving (hollow light blue), saved-fresh (brand blue, tick), saved (brand blue, plain), error (red, "!"). Blue only ever means saved. All reuse the shapes in `save-button.ts`; do not redraw them. The in-page badge draws the same mark inline in `src/content/save-button.ts`, one look per state: hollow grey, in the host's text colour (idle), hollow light blue (saving), solid brand blue with a tick for `SAVED_TICK_MS` then plain (saved), red with "!" (error). The bookmark shape is a licensed Noun Project icon (favorite #8112368)
- Shared constants and types live in `src/shared/` — popup and sidepanel import from shared, never from each other
- Background service worker (`src/background/service-worker.ts`) is the sole bridge to native messaging — thin MV3 wiring that delegates to `src/shared/native-messaging.ts` for port lifecycle
- Toolbar icon (`src/background/toolbar-icon.ts`) paints each tab idle or saved from a `lookup_urls` request on every navigation/tab switch, and shows a save's progress only when the tab's current URL is exactly the saved URL (an in-page post save leaves it alone). Answers are dropped if the tab has moved on (`tabs.get`), and refreshes never override a save's look. Its in-memory state is only an optimisation; it must work after a cold worker start. `tabs` is an *optional* permission (granted from Settings): without it tab events are ignored and the icon changes only from a save's progress and from `report_page`, which the content script sends for its own top-frame URL on LinkedIn/X/HN (the worker accepts it only when the URL equals `sender.url`). Its listeners are registered at top level and gated by the cached permission flag, kept current by `permissions.onAdded`/`onRemoved`
- Native messaging client (`src/shared/native-messaging.ts`) owns `connectNative()`, FIFO response matching, reconnect policy, and connection status — no other module should touch the native port directly. `sendOneShot` (`sendNativeMessage`) is used only for `choose_folder`, whose dialog can outlast the port timeout
- Setup gate (`docs/setup-contract.md` is the source of truth for wire names and states): `src/shared/useAppState.ts` turns `status`/`get_setup_state` into one app state (not installed, forbidden, worker unreachable, crashed, update required, setup required, ready) and polls every 2 s only in the contract's polling states while the surface is open. Popup and side panel render `InstallPrompt` (screens A/B via `AppMissing.tsx`), `UpdateRequired`, or `SetupForm` (screen C) until ready. The platform table, install methods and commands live in `src/shared/platforms.ts`; URL/ID constants in `constants.ts` that are `""` hide their option, never render a dead link. The setup draft (`setup-draft.ts`, session storage) survives the popup closing during the folder dialog
- Wire-contract types (`src/shared/types.ts`) mirror the Rust `native::messages` schema exactly (snake_case fields, same discriminator tags) — do not introduce camelCase alternatives
- Popup owns toolbar action click (`_execute_action` command) — sidepanel open is additive via action-context menu item and named `open_side_panel` command. Do not use `openPanelOnActionClick` or it will regress the popup. The action menu's "Settings" item writes `SIDEPANEL_VIEW_KEY` and calls `sidePanel.open` synchronously inside the click (user-gesture rule)
- Side panel (`src/sidepanel/`) uses list/detail view state without a router — `SidePanel.tsx` is the stateful container, `BookmarkList.tsx`, `BookmarkCard.tsx`, `BookmarkDetail.tsx`, `TagManager.tsx`, and `EditableField.tsx` are presentational. A header switch toggles Bookmarks/Settings (`SettingsView.tsx`, screen D) once the app is ready; Settings sends only changed fields in `save_settings`, and the `tabs` switch calls `permissions.request`/`remove` directly from its click handler
- Native list requests use a narrow `BookmarkSummary` DTO (DB-only, no bundle reads) — keep list payloads bounded and filter server-side
- Native detail requests use a `BookmarkDetail` DTO (DB + bundle summary, no article body) — keep detail payloads bounded
- Shared form controls (`src/shared/TagInput.tsx`, `src/shared/CollectionSelect.tsx`) are used by both popup and sidepanel — popup re-exports from shared. Do not copy form controls into sidepanel or popup; edit the shared originals
- CLI-unreachable onboarding is shared: `src/shared/connection.ts` (`classifyConnectionError` maps Chrome's error strings to `not_installed` / `forbidden` / `worker_unreachable` / `host_crashed`; `registerCommand` lives here; the install commands are `cliCommand`/`fromSourceCommand` in `src/shared/platforms.ts`, which add `--extension-id` only when the running ID is not `WEB_STORE_EXTENSION_ID`; `SETUP_GUIDE_URL` is in `src/shared/constants.ts`) and `src/shared/InstallPrompt.tsx` (install command + register command + reload for `not_installed`, register + reload for `forbidden`, reload only for `worker_unreachable`, reload then register for `host_crashed`; Try again re-runs the caller's request). The popup shows it in place of "Save Failed" for all but `host_crashed` and retries the same save target; the side panel shows it in place of the list
- Test setup (`src/test/chrome-mock.ts`) provides lightweight Chrome API mocks for vitest — use `resetChromeMock()` in `beforeEach` and `createMockPort()` for port lifecycle tests

## Desktop App

- `packages/app/` — installer, setup and settings window. Small fixed window, single instance, no tray; it quits when the window closes. Commands in `src-tauri/src/lib.rs` are thin; launch steps and settings calls live in `src-tauri/src/steps.rs` over an injectable `AppPaths` (tests use a temp HOME), and every rule lives in `agentmark::setup`. Do not add setup logic to the app
- Every launch runs three idempotent steps (`install_cli` from the sidecar + `link_cli`, `register_native_hosts`, `install_skill`); the store ID is always registered, so no pasted ID is needed ("no extension IDs", a waiting state rather than a failure, only happens in a build with an empty store ID). The Extension screen shows the unpacked steps while `WEB_STORE_URL` is empty; pasting an ID is a collapsed option for a copy with another ID. Liveness: the "Add the Chrome extension" screen polls `read_connection` every second while open
- Development run (`npm run tauri dev`, a debug build outside a `.app`; `DevRun` in `steps.rs`): the CLI step leaves `~/.agentmark/bin/agentmark` alone and says so, because the dev "sidecar" is whatever `target/debug/agentmark` the last build left. `AGENTMARK_DEV_INSTALL_CLI=1` copies it anyway (build it after the extension so it embeds it)
- Sidecar: `scripts/build-sidecar.sh [--debug] [--target T]` builds the extension, then `agentmark`, into `src-tauri/binaries/agentmark-<triple>` (gitignored). `externalBin` is only in the overlay `src-tauri/tauri.bundle.conf.json`, so plain `cargo build -p agentmark-app` never copies the sidecar over the CLI's own `target/<profile>/agentmark`. Bundle with `npm run app:build` / `app:build:debug` (`scripts/build-app.sh`), output under `target/[<triple>/]<profile>/bundle/`
- App checks, from `packages/app/`: `npm run typecheck && npm run lint && npm run test && npm run build`; from the root: `cargo fmt --check && cargo clippy -p agentmark-app --all-targets -- -D warnings && cargo test -p agentmark-app`. Root `cargo build`/`test` skip the app (`default-members`)
- The frontend calls commands only through `src/api.ts`. Tests and the browser preview mock them with `mockIPC` (`src/mock/`); `npm run dev` in a plain browser loads `src/dev-mock.ts` (`?scenario=…&view=…`, see its header). Copy, the mark's path data and the summaries wording are copies of the extension's (`src/copy.ts`, `src/components/AgentMarkMark.tsx`); `src/sync.test.ts` fails when they drift. Icons: `scripts/build-icons.sh` renders `packages/extension/icons/icon.svg`; never redraw
- Constants (`WEB_STORE_URL`, `SITE_URL`) live in `src/constants.ts`. Updates are off until `plugins.updater.pubkey` and `endpoints` are set in `tauri.conf.json` (the one switch, see `src-tauri/src/updates.rs`) and the `TAURI_SIGNING_PRIVATE_KEY` secret exists

## Installer

- `install.sh` — Root installer script (POSIX shell). Supports both repo-local and bootstrap (`curl | bash`) execution. Never prompts and never runs `agentmark init`: setup happens in Chrome or the desktop app
- Downloads a release binary, or builds from source (repo checkout or `--from-source`: needs `cargo` and `npm`, runs `npm ci && npm run build` in `packages/extension` before `cargo build --release -p agentmark` so the extension is embedded). Installs to `~/.agentmark/bin/agentmark`, symlinks `~/.local/bin/agentmark`
- Then `agentmark install-extension [--extension-id ID]` (native host registration, development copy of the extension) and `agentmark add-skill`. Exit 1 if the binary is not installed or `install-extension` fails; a skill failure is a warning
- Ends with "Done. Go back to Chrome: …". When `install-extension` prints its "No extension IDs are known yet" note (`NO_EXTENSION_IDS_NOTE`, matched by text), it shows the labelled development steps (load unpacked, `--extension-id` command) instead; that only happens in a build with an empty store ID. After a successful registration it adds a short hint to load `~/.agentmark/extension` unpacked if that copy exists (it carries the manifest `key`, so no ID is needed)
- Flags: `--from-source`, `--extension-id ID`, `--help`; `--skip-init` is accepted and ignored
- Env overrides: `AGENTMARK_EXTENSION_ID`, `AGENTMARK_LOCAL_BIN`, `AGENTMARK_ALLOW_ROOT=1` (it refuses to run as root otherwise). There is no `AGENTMARK_HOME`: the binary always goes to `$HOME/.agentmark`, the folder the CLI and app use, so tests isolate with `HOME`
- Installs the binary through a temp file in `~/.agentmark/bin` (quarantine removed and ad-hoc signed on macOS) renamed over the old one, never written in place, so a running native host is not killed
- Uses global variables for inter-function communication (not stdout capture) since display functions write to stdout; the one exception captures `install-extension` output to detect the no-ID note
- Tests in `packages/cli/tests/install_script_tests.rs` use temp repo fixtures with fake cargo and npm shims and a fake `agentmark` binary (`FAKE_NO_IDS`, `FAKE_EXT_FAIL`)

## CI

- GitHub Actions workflow: `.github/workflows/ci.yml`
- Two jobs: `rust` (extension build, fmt, clippy, build, test) and `extension` (npm ci, typecheck, build, lint, test)
- `app` job on `macos-latest` (Tauri needs WebKit, not installed on the Linux runners): app frontend typecheck/lint/test/build, `cargo fmt`/`clippy --all-targets`/`test` for `-p agentmark-app`, and a debug bundle with the sidecar. `release.yml` also builds the app (`.dmg`, plus updater files when switched on) beside the CLI archive, signing and notarising only when the Apple secrets exist and writing a warning to the job summary when they do not
- A `web` job runs the website's checks (pnpm install, typecheck, lint, build)
- The `rust` job builds the extension first so `include_dir!` embeds real files into the CLI binary
- CI jobs run on `ubuntu-latest`, so macOS-specific CLI behaviors need an injectable or overrideable seam for tests instead of assuming local macOS binaries exist in CI
- Extension job auto-skips if `packages/extension/package.json` does not exist

## Website

- `web/` — marketing site, one static page at `/` plus `llms.txt`, robots, sitemap, icons and OpenGraph image. Deploys to Vercel with root directory `web` (canonical `https://agentmark.vercel.app`)
- Next.js 16 App Router, React 19, TypeScript strict, Tailwind CSS 4, pnpm. No UI kits or animation libraries; icons are inline SVG
- All commands run from `web/`: `pnpm install`, `pnpm dev`, `pnpm typecheck`, `pnpm lint`, `pnpm build`
- Self-contained: nothing in `web/` imports from outside it, and nothing outside imports from it. Every route must stay statically renderable (no API routes, no server-only runtime features)
- Demo slots live in `web/src/components/demos/*-demo.tsx`: default-exported client components with no props, rendered by the page as-is. Replace a demo by editing its file, not the page. Shared frames, the mark, hooks and sample content are in `demos/kit/`; rules and sizes in `demos/README.md`
- Copy must match the repo: check every claim against the README, `install.sh`, `release.yml`, the CLI and the extension. No invented numbers, quotes, users, logos, pricing or features. Update the site (and `public/llms.txt`) when a user-facing claim changes, such as release platforms
- Themes follow `prefers-color-scheme` with no toggle. Both themes are hand-written CSS variables in `web/src/app/globals.css`; use the Tailwind token utilities, never raw colours (the mark is the exception)
- The mark is copied from `packages/extension/icons/` into `web/public/mark/` and `demos/kit/agentmark-mark.tsx`. Do not redraw it; if the icons change, copy them again
- The extension links to `https://agentmark.vercel.app/#install` (`packages/extension/src/shared/connection.ts`), so keep the `#install` anchor
